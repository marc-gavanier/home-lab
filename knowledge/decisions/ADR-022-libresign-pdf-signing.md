# ADR-022 — LibreSign for PDF signing, and the certificate that can only be created once

**Date**: 2026-08-03
**Status**: accepted — installed and measured on the Pi (2026-08-02/03)

## Context

Issue #16 left one item after Calendar/Contacts/Tasks and Collabora (ADR-021):
signing PDFs. The choice had been open since the 2026-06-30 assessment —
LibreSign inside Nextcloud, or Stirling-PDF as a separate container. The
services-discovery session of 2026-07-19 closed it on licensing: Stirling-PDF
moved certificate-based signing to a paid tier during 2026, leaving its free
build a general PDF toolbox rather than a signing tool.

ADR-021 deferred LibreSign explicitly, on the grounds that "its Java and CFSSL
prerequisites are a different problem". Half of that turned out to be obsolete.

## Decision

Enable the **LibreSign app (14.1.0)** inside the existing Nextcloud, with the
**OpenSSL certificate engine** and a self-signed root CA generated by the
deploy. No new container, no Traefik route, no port, no permanent RAM.

### CFSSL is not needed, and that removes most of the difficulty

LibreSign's default certificate engine is now `openssl` — `Command/Install.php`
reads `certificate_engine` with `'openssl'` as its fallback, and
`libresign:configure:openssl` generates the root CA through PHP's own OpenSSL
binding. CFSSL, a Go binary from Cloudflare that the older documentation
presents as a prerequisite, is only one of two possible engines.

So the install is deliberately **not** `libresign:install --all`, which the
documentation recommends: `--all` includes `--cfssl` and would put a certificate
authority we never call on the disk. The three flags we pass are `--java`,
`--jsignpdf`, `--pdftk`.

`roles/deploy/tasks/libresign.yml` re-asserts the engine when it drifts. The
admin UI offers the switch, and flipping it points LibreSign at a CA that does
not exist — a failure that surfaces at signing time, not at the switch.

### Java is needed, is downloaded at runtime, and lives outside the image

The signature itself is produced by **JSignPdf**, a Java program. LibreSign
downloads a JRE, the JSignPdf jar and pdftk into Nextcloud's appdata the first
time it is set up — they are not in the image, and a rebuilt container does not
carry them:

| | Measured on the Pi |
|---|---|
| Java | Temurin **21.0.8**, `aarch64`, glibc build (the container is Debian, not Alpine) |
| Total on disk | **185 MB** under `appdata_*/libresign/aarch64/` |
| Download + extract | **22 s** |
| Permanent RAM | **0** — the JVM runs only while a document is signed |

Architecture and distribution are auto-detected inside the container
(`php_uname('m')`, then the container's own os-release), so nothing needs
pinning for arm64. Integrity is checked: the JRE against the SHA-256 checksum
published beside the Adoptium release, JSignPdf and pdftk against MD5 constants
compiled into the app — weak as a hash, but over HTTPS to a release URL, and not
ours to change.

The binaries are **excluded from the backup** (`resticprofile.yaml`, the
`backup.exclude` list — `backup.sh` until ADR-031): 185 MB that one
command rebuilds is not worth copying offsite over the parents' uplink. The
exclusion is scoped to the architecture directory, because the root CA sits in
a *sibling* directory under `libresign/` and must never leave the backup set.

### `sun.jnu.encoding` was ASCII, and it is invisible until an accent appears

LibreSign's own setup check flagged it, and the JVM confirms it. Measured in the
running container, before any change:

```
file.encoding   = UTF-8
native.encoding = ANSI_X3.4-1968
sun.jnu.encoding = ANSI_X3.4-1968
```

`file.encoding` is UTF-8 whatever the environment says — that has been Java's
default since JEP 400 — which is exactly what makes this easy to dismiss.
Strings *inside* the JVM are fine. The **boundary** is not: `sun.jnu.encoding`
decodes the command-line arguments and file paths handed to JSignPdf, and the
image sets no locale at all, so Java derived plain ASCII from an empty
environment. Every accented character in a document name or a signature reason
crosses that boundary.

`LANG` and `LC_ALL` set to `C.UTF-8` on the Nextcloud container bring all four
encodings to UTF-8 — verified with the same command before and after. `C.UTF-8`
rather than a `fr_FR` locale on purpose: it is present in the image without
generating anything, and the only thing being fixed here is the character set,
not the collation or the message language.

### The root certificate is generated once, and the code makes that dangerous

`libresign:configure:openssl` calls `InstallService::generate()`, which passes
an **empty** config path. That deletes the stored `config_path` key, bumps
`ca_generation_counter`, and makes the engine initialise a **fresh PKI
directory** — a new certificate authority. Every certificate already issued from
the previous one then validates against a root nobody holds anymore.

Nothing in the command's output says so, and it exits 0.

So the deploy guards it on the CA files themselves — `ca.pem` *and* `ca-key.pem`
under the recorded `config_path` — rather than on a flag or on the presence of
that path. The directory is created when the app is installed, well before any
CA exists; a guard on the path would have skipped the generation forever, and a
guard on a "done" marker would never repair a generation that died halfway.
Both files present means never touch it. Either missing means retry.

This is the same lesson as the richdocuments discovery cache in ADR-021, in the
other direction: **a step that must run exactly once needs its condition read
from the artefact, not from the intent.**

The identity that goes into it (`libresign_cert_cn/_o/_c`) is read only at
generation. Editing those variables afterwards changes nothing — regenerating
is the only way to apply them, and regenerating is what this guard exists to
prevent.

### Signing runs in the web container, and that is load-bearing

`signing_mode` defaults to `sync`, so JSignPdf is spawned by the PHP process
handling the request. The Nextcloud container has a writable root filesystem, so
its `/tmp` is the writable layer on `/mnt/data` — no size limit worth naming.

Switching LibreSign to `async` moves signing into the queued jobs picked up by
**`nextcloud-cron`**, which is `read_only: true` with a **32 MB tmpfs on
`/tmp`**. Nextcloud has no `tempdirectory` configured, so PHP's temp files land
there, and a signature copies the PDF in and the signed result out. Documents of
a few MB would work and a large scan would not, with the failure appearing in a
background job rather than in front of the user. Left as `sync`, and written
down here because the toggle exists in the admin UI and its cost is nowhere near
it.

## Consequences

**Signatures are self-signed, and readers will say so.** The root CA is ours, so
Acrobat and Firefox's viewer report "signature validity unknown" until the
recipient imports `ca.pem`. That is the honest ceiling of self-hosted signing:
it proves the document has not changed since signing, and it does not prove
anyone else's trust in who signed it. An eIDAS-qualified certificate is the only
thing that changes that answer, and it is bought, not generated.

**The CA private key is now part of the disaster-recovery surface.**
`ca-key.pem` lives in `appdata_*/libresign/pki/<id>/` inside the Nextcloud data
directory, which is on the LUKS volume and inside the restic set — so it is
covered by the existing backup, and by ADR-011's premise that secrets live on
`/mnt/data`. It is not in `/mnt/data/secrets`, because LibreSign resolves the
path itself and a symlink there would break the way #27 broke SearXNG. Losing it
does not lose the signed documents; it loses the ability to issue new
certificates under the same root.

**`poppler` reports `info`, and it stays that way.** `pdfsig` and `pdfinfo` are
absent from the Nextcloud image. In LibreSign 14 neither is required: signature
validation is pure PHP (`PdfSignatureValidationService` — "this replaces shell
calls to pdfsig"), and page dimensions fall back to the bundled Smalot parser.
Installing them would mean building a custom Nextcloud image for two binaries
the app no longer calls — the same trade the SearXNG branding declined (#27).

**The deploy fails when signing would fail.** Two probes: the JRE is *started*,
not just found on disk — the check that catches a JRE the container's libc
cannot load — and `libresign:configure:check` must report no `error` row. `info`
rows do not fail the deploy; that is what makes the poppler note above a note.

**LibreSign is not the answer to "put my signature on this PDF".** Found the
evening it went live, by trying to use it: its request-then-sign ceremony exists
to collect signatures from *other people*, and there is no shortcut through it
for a solo stamp. Nextcloud's own PDF viewer already does that — `editorStamp`
with *Add image*, plus freehand ink and free text, in the deployed
`files_pdfviewer` templates, gated by no setting. So the two coexist by purpose,
not by preference: the viewer for the image an administrative form expects,
LibreSign for a signature that has to be verifiable. Worth stating in the ADR
because the obvious reading of "we deployed a PDF signing tool" is the wrong
one, and the cheaper tool was installed all along.

**No Uptime Kuma monitor.** LibreSign has no endpoint of its own; it is up
exactly when Nextcloud is, and that is already monitored. The failure modes it
does have are configuration ones, and the deploy is what checks those.

**Renovate does not see this.** Nextcloud apps come from the appstore, not from
an image tag, so LibreSign updates arrive through Nextcloud's own app updater
rather than through a pinned version in this repository. The version its
binaries must match travels with the app, which is why `libresign:install` is
conditioned on the binaries being *usable* rather than merely present.
